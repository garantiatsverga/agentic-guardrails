# Document Agent

Прототип интеллектуальной обработки документов для кредитных заявок малого и среднего бизнеса. 

Система автоматически извлекает данные из пакета документов, проверяет их на согласованность, валидирует и формирует структурированный JSON для передачи в скоринг. Проект включает в себя как полностью рабочий агент извлечения данных (Document Agent), так и симуляцию полного процесса обработки заявки (оркестрация, скоринг, комплаенс).

**Весь интерфейс работает через командную строку (CLI).** Мы сознательно отказались от веб-интерфейса в первой итерации, чтобы сфокусироваться на ядре обработки данных и журнале аудита.

## Быстрый старт

Требования: **Python 3.10+**.

```bash
# 1. Создание виртуального окружения
python -m venv .venv
source .venv/bin/activate  # Для Windows: .venv\Scripts\activate

# 2. Установка
pip install -e .

# 3. Сборка и тесты (кроссплатформенный скрипт)
python build.py

# 4. Запуск интерактивного CLI-меню
python main.py
```

## Что умеет система

### 1. Document Agent (Реальная логика)
Основной рабочий модуль, который выполняет всю реальную работу с файлами:
*   Принимает 1–3 файла (PDF или TXT) до 10 МБ каждый.
*   Извлекает текстовый слой (используется библиотека `pdfplumber`).
*   Определяет роль каждого документа (Анкета, Финансовая отчётность, Описание бизнеса) на основе имени файла и набора полей.
*   Склеивает данные из нескольких документов, используя приоритеты (например, сумма кредита берётся из Анкеты, а выручка — из Финансовой отчётности).
*   Обнаруживает **конфликты** (если в анкете сумма 1 млн, а в выписке 10 млн — система пометит это как `warning` и отправит заявку на ручную проверку).
*   Проверяет данные по 6 правилам (наличие обязательных полей, формат ИНН, положительная сумма и т.д.).
*   Формирует структурированный JSON-ответ для скоринга.

### 2. Полный процесс (Симуляция / МОК)
Демонстрация того, как Document Agent встраивается в общий процесс обработки кредитной заявки:
*   **Discovery-фаза:** назначение R-level (уровня автономии), бюджета токенов и списка политик.
*   **Маршрутизация:** построение маршрута из 8 этапов (Оркестратор → Document Agent → Scoring → Compliance → Review → HITL).
*   **Скоринг и Комплаенс:** симуляция ответов от Scoring Agent (балл 685/1000, серая зона) и Compliance Agent (проверка политик).
*   **HITL:** эскалация на андеррайтера при пограничных суммах.
*   **Evidence Bundle:** формирование паспорта заявки.

> **Важно:** В режиме «Полный процесс» реально работает **только Document Agent** и модуль аудита. Оркестратор, Скоринг, Комплаенс и HITL — это предзаполненные моки (МОК), которые имитируют ответы будущих микросервисов. Это сделано для демонстрации сквозного сценария.

## Как это работает (архитектура)

Проект разделён на два слоя:
1.  **`document_agent/`** — прикладной слой. Здесь находится парсинг документов, валидация и CLI-интерфейс.
2.  **`agentic_guardrails/`** — библиотека предохранителей. Обеспечивает надёжность: защиту от каскадных сбоев (`FailureBreaker`), ограничение бюджета (`CostBreaker`) и неизменяемый журнал аудита (`AuditChain`).

### Журнал аудита (Tamper-Evident)
Каждое действие системы (загрузка файла, извлечение, валидация, эскалация) записывается в `AuditChain`. 
Каждая запись содержит SHA-256 хеш предыдущей записи. Если изменить хотя бы один байт в истории, цепочка порвётся, и метод `verify()` вернёт `False`. Это гарантирует, что историю обработки заявки невозможно подделать задним числом.

## Тестовые документы

В папке `tests/fixtures/` лежат готовые PDF-файлы для проверки:
*   `case1_success.pdf` — идеальная заявка.
*   `case2_partial.pdf` — заявка без ИНН.
*   `case3_escalate.pdf` — заявка на 10 млн (требует внимания).
*   `case4_failed.pdf` — битый файл.
*   `real_docs/` — пакет из 6 документов (Анкета, Паспорт, Выписка, КУД, ЕГРИП, ПТС), имитирующих реальный пакет документов для полного процесса.

## Ограничения и упрощения

В рамках текущей итерации мы сознательно упростили некоторые компоненты, чтобы сфокусироваться на работе ядра:

*   **Нет OCR.** Система работает с текстовым слоем PDF. Если загрузить скан или фотографию (без текста), система вернёт статус `failed` и отправит заявку на ручную проверку. Поддержка OCR для изображений — задача следующего этапа.
*   **Моки вместо внешних систем.** Запросы в ФНС, ЕГРЮЛ, БКИ и вызов скоринговой модели заменены предзаполненными моками. В прототипе они показывают, как будет выглядеть результат, но не делают реальных сетевых запросов.
*   **In-memory хранилище.** Результаты обработки и журнал аудита хранятся в оперативной памяти процесса. При перезапуске история очищается.
*   **Нет LLM.** Извлечение данных работает на детерминированных правилах и регулярных выражениях. Это гарантирует, что один и тот же PDF всегда даст один и тот же JSON (что критично для кредитного скоринга). Использование LLM для генерации объяснений или OCR запланировано на следующие итерации.
*   **Нет веб-интерфейса.** Вся работа происходит через CLI. Это позволяет показать логику работы агента без накладных расходов на фронтенд.

Подробный список упрощений и соответствие реальному процессу описан в файле `docs/simplifications.md`.

## Структура проекта

```
document-agent/
├── main.py                      # Точка входа (интерактивное CLI)
├── build.py                     # Кроссплатформенный скрипт сборки и тестов
├── document_agent/              # Продукт (прикладной слой)
│   ├── models.py                # Pydantic-модели (JSON-контракт)
│   ├── extraction.py            # Парсинг PDF, роли, слияние, конфликты
│   ├── validation.py            # Валидация через HookBus
│   ├── escalation.py            # Логика эскалации
│   ├── pipeline.py              # Пайплайн (шаги 1-5)
│   ├── agents_mock.py           # МОКИ для скоринга/комплаенса
│   ├── orchestrator_mock.py     # МОК Оркестратора
│   └── cli.py                   # Вспомогательные функции CLI
├── agentic_guardrails/          # Библиотека предохранителей
│   ├── audit.py                 # AuditChain (tamper-evident)
│   ├── failure_cb.py            # FailureBreaker (защита от сбоев)
│   ├── cost_cb.py               # CostBreaker (бюджеты)
│   ├── policy_hook_bus.py       # Шина правил
│   └── ...
└── tests/                       # Тесты и фикстуры
```

## Тестирование

Проект покрыт двумя уровнями тестов:
1.  **Unit-тесты:** проверка парсинга каждого поля, ролей документов и логики валидации.
2.  **Integration-тесты:** проверка пайплайна на 4 кейсах, реальных документах и конфликтах.

Запуск всех тестов:
```bash
python build.py
```

Или напрямую:
```bash
pytest tests/ -v
```
